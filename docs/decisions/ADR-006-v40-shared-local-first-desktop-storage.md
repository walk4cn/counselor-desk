# ADR-006: v4.0 共享业务核心与桌面可靠本地仓库

## Status

Accepted

## Date

2026-08-12

## Context

v4.0 同时维护单文件网页端和 Windows 桌面端。两端必须保持字段、导入导出、附件和预警规则一致，同时桌面端需要解决异常退出、刷新后数据消失、附件丢失和旧版迁移不可追溯等问题。仅依赖浏览器 `localStorage` 无法满足大附件、恢复点和原子写入要求；仅把数据写入 SQLite 又会削弱便携 HTML/JSON 的可迁移性。

## Decision

- 业务规则和数据契约集中在 `src/core/v4-runtime.js`，网页端使用 IndexedDB + 备份文件，便携 HTML 继续作为离线迁移入口。
- 桌面端在系统用户目录建立 JSON 快照、SQLite 结构化索引、事务日志、受管附件目录和带附件旁车目录的恢复点。每次 renderer 写入先原子替换 JSON，再同步 SQLite；读取时选择时间更新的有效快照。
- 附件由主进程复制、限制单文件 25MB、使用 SHA-256 哈希去重，并以 `recordId__attachmentId` 命名；删除按完整记录前缀匹配，避免相邻 ID 误删。
- 关闭窗口前由主进程等待 renderer 快照写入；定时恢复点默认保留最近 20 份。损坏快照只进入恢复保护，不以示例数据覆盖原文件。
- NSIS 卸载默认保留用户数据；用户明确选择删除数据后才清理数据库、附件和恢复点。界面锁仍只是访问控制，不宣称数据库加密。

## Alternatives Considered

### 仅使用 localStorage

实现最简单且无需桌面原生模块，但容量、写入原子性和附件恢复能力不足，无法解决已报告的数据丢失问题，拒绝。

### 仅使用 SQLite

事务和查询能力更强，但会让网页端和便携 HTML 失去同一份可交换格式，也增加原生模块迁移成本；作为桌面结构化索引保留，作为唯一格式拒绝。

### 云端同步

可解决跨设备同步，但需要账号、服务器、冲突合并和敏感学生数据治理。本版本明确保持本地优先，不引入未授权的数据出域。

## Consequences

- 桌面端启动、异常退出、迁移、备份恢复和卸载均可独立验证，且 JSON 快照仍可人工检查和跨端迁移。
- 每次编辑会产生快照/事务日志写入；长期运行依赖恢复点保留策略和后续压缩工具。
- SQLite 原生依赖需要按目标 Electron 版本重建；无原生模块时 JSON 仍提供可恢复降级路径。
- 单文件网页仍受浏览器容量和权限限制，大附件/视觉回归必须在真实浏览器和目标 Windows 环境继续验收。
